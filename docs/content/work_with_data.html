How to Work with Data

With the migration to the cloud, there is a lot going on now. Lots of new ways to connect with data and major changes to many of our workflows. We are all learning together. We probably made some mis-steps with how data were migrated to the cloud, and we probably don’t yet know all the ways that we’ll work with data moving forward. Be patient with yourself and each other!

Here are some great resources for learning more about the Google cloud offerings.

For suggestions, updates, or errors, please submit an issue on GitHub.

Individual Resources

The two options available for storing individual files (such as administrative documentation, working copies of files, etc.) are your laptop or individual Google Drive (“My Drive”). No original or processed data should be stored exclusively in any of these resources. It is personal preference what you store where. Refer to Basics for suggestions for file naming and folder organization.

Backup/Recovery Procedures

Laptop

Your laptop needs to be set-up to back files up to Google Drive using Google Drive Desktop. Once configured, the folder(s) you select for back-up will be visible from the Google Drive website (under “Computers” in the left navigation pane).

Google Drive

The files you store on Google Drive are backed up using Google specifications:

  • Google keeps a versioning history of files that can be viewed/recovered within the web browser.
    • For G-suite files can be viewed within the file (File/Version History).
    • For all other files (e.g. CSV files, Access DBs, pdfs) can be viewed through the web browser.
      • Click on the 3 dots to open up the “More actions” options for the item of interest.
      • Click File informationversions.
      • Through this list of files, you can identify which version of a file to which you want to revert.
  • To recover files, you need to act quickly:
    • Within the first 30 days of a file being deleted, you can recover it via the Google Drive trash.
    • After 30 days, the file can no longer be recovered.

Virtual Machine

Virtual machines (VMs) are a great option for accessing cloud-based data when you need access to more than one piece of software. Example use cases for a VM are image-based analysis, spatial data access and analyses using QGIS or ArcGIS, opening Access databases, etc.

This workflow details the process for obtaining a virtual machine, and requests for virtual machines can be made here. In the request form, there are different options available for CPU and GPU. For most cases, a basic configuration will be more than sufficient for PEP work. Due to costs, the “high GPU” will need to be justified and will require Division Director approval.

A few things to note:

  • You need to “Start/Resume” a VM resource before connecting to it through Remote Desktop Connection and “Stop” a VM when your work is complete. This is the equivalent of booting up and shutting down. Use this site to complete these actions.
  • WARNING: you will get an email if your VM sits idle for more than 12 hours (that will make you not want to forget again).
  • The cost for a VM is based on active use. If you expect to have any need for one, make the request and get it set-up!
  • The Self Service Portal is available within the VM, so the software installation experience is the same as your laptop (see Software Requirements and Recommendations above).
  • VMs can have a number of shared users assigned to a VM and up to two concurrent users. Since costs are based on active use, it is only in rare cases that we should need to share a VM (e.g. KAMERA post-processing GPU).
  • GPUs can be limited within a region – LLMs are hogging the resources at the moment, so you might not always be able to start a GPU VM when you need it.
  • Accessing our bucket and database comes as no cost when using a VM. There is a cost for the same activities when working from your laptop.
  • OFIS will be monitoring usage and you will be contacted if the compute needs exceed what is actually used.

Remote SSH into VM from Positron

There is a nifty trick for connecting to a Linux VM via Positron (using a remote SSH connection) to take advantage of the VMs compute resources while working in R on your laptop:

  1. Open the Command Palette: Press Ctrl+Shift+P (Windows/Linux) or Cmd+Shift+P (macOS) inside Positron.
  2. Find the Remote Menu: Type Remote Menu and select Remote SSH: Show Remote Menu.
  3. Connect to Host: Click Connect to Host and enter your VM’s hostname and login credentials (like your username and SSH key or password).
  4. Work on the VM: Once connected, a small indicator will appear in the bottom-left corner. The file explorer will now show the files living inside your VM instead of your local computer.

Note: Your VM must be running Linux and have at least 2 GB to 4 GB of RAM to run the remote Positron server smoothly.

GCP Bucket

There are some fundamental differences in how we work with data in a bucket versus how we work with data on a local machine or in a shared drive.

  • Data in a bucket are stored as objects, so folders are useful for our organization, but not necessary for the bucket to function.
  • Data in a bucket are not stored on your local machine, so data are downloaded to your local machine or virtual machine when you work with it. This is different than a shared drive, where the data are stored on a server and you can work with the data without downloading it to your local machine.
  • Data in a bucket cannot be modified the same way as files are on a local machine or shared drive.
    • The only actions you can take on data in a bucket are read, write, and delete. No modify!
    • You will need to download the data, modify it, and then upload it back to the bucket. This is different than a shared drive, where you can modify the data directly on the server.
    • This also applies to renaming files, so it’s best to ensure the data are named properly and are organized based on the project protocols before the data are uploaded to a bucket.

There is no cost to move data into a bucket, but there are costs for storing, accessing, and modifying the data in our buckets when data are pulled to our local machines. When we work with the data from a workstation or virtual machine (that are stored in the same region as our bucket), there is no cost to working with the data (though there is a cost to having a VM or using a workstation). Each program’s costs are heavily monitored, and we will be notified (individually and/or programmatically) if our usage is anomalous. For now, be aware of how you’re interacting with the buckets, and reference this chart as guidance (not authority) to help you get started selecting the right tool you use for connecting to the data.

General guidance when working with data in a bucket:

  • Use your laptop for light access
  • Use a workstation for R, Python, or Visual Studio code development and execution
  • Use a virtual machine if you need access to software beyond those offered from a workstation (e.g. DIVE annotation)

Authentication

Authentication for bucket access is limited to 16-hour time windows, meaning your process will be interrupted if it is actively working with bucket data for more than 16 hours. This is most likely to impact AI/ML training and any potential long-running processes. This is a recent change so more details will be provided about alternative methods for authentication as more information is available. For now, be aware of this limitation and plan accordingly.

Uploading Data to a Bucket

There are a few ways to upload data to the bucket:

  • In the web browser (best for small numbers of files)
  • Using the most recent version of the Cloud Data Transfer Tool (preferred method)
    • This tool is available through the Self Service Portal
    • Follow these instructions to configure and move data
    • This tool supports extended connection to the bucket, so you will not be required to authenticate every 16 hours!
  • Using NOAA Jetstream (not supported by OFIS)
    • Download from this repository and follow the instructions in the README
    • Requires the installation of Python and Powershell

Editing Data in a Bucket

Changes to data made in the bucket should be made sparingly and via the command line in a web browser. One of the most common changes is reorganizing or renaming data. To do so

gcloud storage mv [old_location] [new_location]

There are various wildcards (*) that can be used in this command to apply specific changes to your data.

Backup/Recovery Procedures

Data are backed up based on AFSC back-up and recovery procedures: - 30 days “soft delete” (i.e. recycle bin) - Versioning: keep the most recent 5 versions of a file - Storage Class: Autoclass (storage becomes cheaper over time for unaccessed data) - Our data will move between hot and almost as hot classes - Data will not go down to the coldest data classes because of cost to move between tiers - We can evaluate options in time to move our least access data to archival cold buckets where it will require a service desk ticket for access - Disaster Recovery Snapshots (i.e. copies stored elsewhere) - Monthly snapshots for 12 months - Annual snapshots for 7 years

Connect from Workstation

If using an R workstation, use this script to mount buckets to R using the Terminal.

# Terminal code for mounting Google Cloud Buckets to Google Cloud Workstations
# Author: Alexandra Norelli with Gemini assistance for R to BASH translations.  
# Run the .sh file with the code commented below and follow the instructions to 
# authenticate your google account.  

# Run this script as a .sh file by copying and pasting this code in your bash 
# terminal:  
#bash mount_bucket_folder.sh

# Define your bucket and the mount point.
# replace "nmfs-opensci" with your bucket name
# add the path to folder within the bucket for FOLDER_NAME
# make sure to put a / at the end of the folder path
# The `$HOME` symbol is a shortcut for your home directory, so this will
# create the folder at /home/your_username/my_gcs_bucket.
BUCKET_NAME="user_to_specify"
FOLDER_NAME="user_to_specify"
MOUNT_POINT="$HOME/user_to_specify"

# --- Authentication ---
# This command authenticates your user account with Google Cloud.
# You'll be prompted to open a browser to complete the login process.
echo "Running gcloud authentication. Please follow the instructions to log in in your browser."
gcloud auth application-default login --no-launch-browser

# --- Installation and Setup (Run only once) ---
# Create the mount point if it doesn't exist.
# Since this directory is in your home folder, you don't need `sudo` to create it.
if [ ! -d "$MOUNT_POINT" ]; then
    mkdir -p "$MOUNT_POINT"
fi

# Add the Google Cloud GPG key to your system's trusted keys.
# This is a critical step to verify the authenticity of the packages.
curl -fsSL https://packages.cloud.google.com/apt/doc/apt-key.gpg | sudo gpg --dearmor -o /etc/apt/trusted.gpg.d/gcsfuse.gpg

# Add the GCS FUSE repository to your system's sources list.
echo "deb [signed-by=/etc/apt/trusted.gpg.d/gcsfuse.gpg] https://packages.cloud.google.com/apt gcsfuse-`lsb_release -c -s` main" | sudo tee /etc/apt/sources.list.d/gcsfuse.list > /dev/null

# Update the package list to include the new repository.
echo "Updating package list..."
sudo apt-get update

# Install gcsfuse.
echo "Installing gcsfuse..."
sudo apt-get install -y gcsfuse

# --- Mounting the Bucket ---  you might only need to run this if restarting a workstation
# Use the gcsfuse tool to mount the bucket to the specified mount point.
# The mount point is in your home directory, so `sudo` is no longer needed.
echo "Mounting the bucket..."
gcsfuse --implicit-dirs --only-dir "$FOLDER_NAME" "$BUCKET_NAME" "$MOUNT_POINT"

echo "Mounting complete. You can now access the bucket contents at $MOUNT_POINT"

# Optional: List the contents to verify the mount was successful.
ls -l "$MOUNT_POINT"

PostgreSQL Database

This section details the different methods for connecting to the PostgreSQL database using Microsoft Access, R, QGIS, and ArcMap/Catalog/Pro software.

Backup/Recovery Procedures

The database runs on a scheduled back-up routine (7 daily back-ups). If a substantial error in data has been made (e.g. table deleted, records are completely untrustworthy), contact S. Koslovsky ASAP to get the table restored. The following steps will be applied:

  • Restore from backup to a new, temporary PostgreSQL instance (platform defaults to this manner of restore)
  • Export the individual database or components from the temporary instance that needs to be restored.
  • “Patch” in the exported database components over the live postgres instance database (depending on what’s needed, granular modify or full delete / reupload).

Connect from Microsoft Access

To use any of the project Access front-ends or to create your own connection to the database via Access, you need to have the ODBC connection established. This requires support from an Service Desk Ticket to update your ODBC Data Sources to allow connection to PostgreSQL.

The connection details for setting up the ODBC connection are as follows:

  • Install the ODBC driver with Service Desk Ticket, if not already installed (typically, only when you are working on a new laptop or VM).
    • You will want to download the most recent driver. Click on the most recent folder without “-mimalloc” at the end of the file name; install the psqlodbc_x64.msi version.
    • If you already have this installed, skip to the next step. You do not need to work with OFIS to add the data source.
  • From the start menu, open the ODBC Data Source Administrator (64-bit), click “Add…”.
  • In the list of drivers available, select “PostgreSQL Unicode(x64)” and click Finish.
  • In the PostgreSQL Unicode ODBC Driver (psqlODBC) Setup, enter the following details:
    • Data Source: database_name
    • Description: (leave blank)
    • Database: database_name
    • SSL Mode: allow
    • Server: afsc.postgres.prod.nmfs.local
    • Port: 5432
    • User Name: your_user_name
    • Password: your_password
  • Before saving, click “Test” to confirm the connection to the database.
  • Click “Save” and close the window.

Once configured, you can open any of the program databases and should no longer need to enter your user name and password each time. Hooray! If you are not experiencing this, you might need to update to a newer version of the ODBC driver.

ONLY AFTER WE MIGRATE THE PEP DASHBOARD: If you have a database connection to the old, internal PEP database (pep), delete that from the ODBC connections list.

Connect from R

To connect to the PEP database from R, there are two different steps:

  1. First, create an .Renviron file to store the connection details to the database. This only needs to be done once.
    1. Create a new text file in your Documents folder on your laptop (typically in C:.LastName) named “.Renviron”. There will be no file name and the file extension is Renviron (weird, I know).
    2. Open the file in a text editor (Notepad or Notepad++).
    3. Enter the following details and save the file. Replace the [database_name] at the start of the line for each of these variables with the database to which you are connecting (e.g., mml_pep_ip).
[database_name]_ip <- afsc.postgres.prod.nmfs.local
[database_name]_port <- 5432
[database_name]_db <- database_name
[database_name]_user <- your_user_name
[database_name]_user_pw <- your_password
  1. Second, connect to the database during an R working session. You will need to do this each time you connect to the database. The following steps are required:
    1. Ensure you have the RPostgres R package installed. Do not use RPostgreSQL, as it is outdated. If you catch S. Koslovsky sharing this package, call her out! :)
    2. Use the following code to create a connection to the DB using the details in your .Renviron file, again, replacing the [database_name] at the start of the line for each of these variables with the database to which you are connecting (e.g., mml_pep_ip).
library(RPostgres)
con <- RPostgres::dbConnect(
  Postgres(),
  host = Sys.getenv("[database_name]_ip"),
  port = Sys.getenv("[database_name]_port"),
  dbname = Sys.getenv("[database_name]_db"),
  user = Sys.getenv("[database_name]_user"),
  password = Sys.getenv("[database_name]_user_pw") #,
  sslmode = "require"
)
c. Once you have this connection established, you can use the RPostgres package to get, query and send data to the database. As an example, the following code will return all details for PEP activity plans stored in the database.
data <- RPostgres::dbGetQuery(
  con,
  "SELECT * FROM administrative.tbl_activity_plans"
)

Connect from QGIS

To view spatial data stored in the PostgreSQL database:

  • Open QGIS.
  • Right click “PostgreSQL” in the Browser window, and select “New Connection…”. NOTE: If you see “PostGIS” instead of “PostgreSQL”, you need to submit a Service Desk Ticket to update your version of QGIS. You should be working with QGIS 3.28 or higher.
  • In the Create a New PostGIS Connection window, specify the following options:
    • Name: database_name
    • Service: (leave blank)
    • Host: afsc.postgres.prod.nmfs.local
    • Port: 5432
    • Database: database_name
    • SSL mode: require
    • Username: your_user_name (check box to save)
    • Password: your_password (check box to save)
  • Click “Test Connection” to confirm the connection to the database and before closing the menu.
  • Once created, you will see a new connection to the database under PostgreSQL. The available data are listed under each schema, and only spatial data are visible (unless you have configured your connection otherwise).

For entering or modifying spatial data, process the data as instructed for each individual project. 

Connection from ArcGIS

To view spatial data stored in the PostgreSQL database in ArcGIS, you will need to create a database connection. This can be done in ArcCatalog or ArcPro:

  • In ArcCatalog in the Catalog Tree, navigate to the “Database Connections” OR in ArcPro under Insert/Connections. Select “Add Database Connection”.
  • In the pop-up window, select or enter the following details:
    • Database Platform: PostgreSQL
    • Instance: afsc.postgres.prod.nmfs.local
    • Authentication Type: Database authentication
    • User name: your_user_name
    • Password: your_password
    • Save user name and password: OK to save!
    • Database: database_name
  • Once connected, you can view all data and add spatial data to your maps.

Do not make any changes to the spatial data from ArcGIS software. QGIS is the authoritative software for editing spatial data stored in PostgreSQL.
